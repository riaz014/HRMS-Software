HRMS PROJECT FULL GUIDE
=======================

1. PROJECT PURPOSE
------------------
This project is a Human Resource Management System (HRMS) with:
- employee management
- salary management
- payroll generation and reporting
- admin and HR user management
- JWT-based authentication and authorization

The system has two main parts:
- Frontend: Angular 18 application in hrms-web
- Backend: ASP.NET Core .NET 8 Web API in src/HRMS.API

The backend stores data in SQL Server through Entity Framework Core.


2. FULL TECH STACK
------------------
Frontend:
- Angular 18
- Angular Material
- Standalone components
- RxJS
- jspdf for PDF export
- xlsx for Excel export
- Angular SSR support with Express in server.ts

Backend:
- ASP.NET Core .NET 8 Web API
- Entity Framework Core
- SQL Server
- JWT authentication
- Swagger support in Development

Database:
- SQL Server instance from appsettings.json
- Current configured connection string:
  Server=localhost\SQLEXPRESS02;Database=HRMSDb;Trusted_Connection=True;MultipleActiveResultSets=true;TrustServerCertificate=True


3. HIGH LEVEL ARCHITECTURE
--------------------------
Frontend sends HTTP requests to backend API.
Backend validates JWT token and role permissions.
Backend uses repositories + services + Entity Framework Core to read/write SQL Server.
Backend returns JSON responses.
Frontend renders tables, forms, cards, dialogs, reports, PDF, and XLSX exports.

Main folders:
- hrms-web = Angular frontend
- src/HRMS.API = API host, controllers, JWT, middleware
- src/HRMS.Application = interfaces and application contracts
- src/HRMS.Domain = entities
- src/HRMS.Infrastructure = EF Core, repositories, services, persistence

4.3 Authentication on frontend
Files involved:
- hrms-web/src/app/core/services/auth.service.ts
- hrms-web/src/app/core/services/api.service.ts
- hrms-web/src/app/core/guards/auth.guard.ts
- hrms-web/src/app/core/interceptors/auth.interceptor.ts

Flow:
1. User logs in from Login page.
2. Frontend calls POST /api/auth/login.
3. Backend returns JWT token.
4. Token is stored in localStorage key hrms_access_token.
5. User object is stored in localStorage key hrms_user.
6. authInterceptor attaches Authorization: Bearer <token> header to outgoing API requests.
7. authGuard protects authenticated pages.
8. loginGuard prevents already logged-in users from returning to login page.

6. DATABASE STRUCTURE
---------------------
Main entity files:
- src/HRMS.Domain/Entities/BaseEntity.cs
- src/HRMS.Domain/Entities/Department.cs
- src/HRMS.Domain/Entities/Employee.cs
- src/HRMS.Domain/Entities/Salary.cs
- src/HRMS.Domain/Entities/Payroll.cs
- src/HRMS.Domain/Entities/AuthUser.cs

Current important tables:
- Departments
- Employees
- Salaries
- PayrollTransactions
- AuthUsers
- __EFMigrationsHistory

6.1 Departments table
Stores department names.
Examples include Faculty, Software Development, Human Resources, Administration, Admissions and Records, etc.
This is auto-seeded on startup.

6.2 Employees table
Stores employee master data:
- EmployeeNumber
- FirstName
- LastName
- Email
- ContactNumber
- Position
- AccountNumber
- EmploymentStatus
- DateOfJoining
- IsActive
- DepartmentId

Important constraints:
- EmployeeNumber unique
- Email unique
- AccountNumber unique

6.3 Salaries table
Stores salary revisions per employee.
Fields include:
- EmployeeId
- BasicAmount
- AllowanceAmount
- DeductionAmount
- EffectiveFrom
- EffectiveTo

One employee can have multiple salary rows over time.
The current salary is usually the row where EffectiveTo is null, but payroll logic now also supports month overlap.

6.4 PayrollTransactions table
Stores generated payroll output per employee per month.
Fields include:
- EmployeeId
- SalaryId
- PayrollYear
- PayrollMonth
- GrossPay
- Deductions
- NetPay
- ProcessedAtUtc

6.5 AuthUsers table
Stores application login users permanently in SQL.
Fields include:
- Username
- Password
- Role
- CreatedAtUtc
- UpdatedAtUtc

This replaced the old in-memory-only user storage so admin-created users survive restart.

Check salaries:
SELECT * FROM Salaries ORDER BY EmployeeId, EffectiveFrom DESC;

Check payroll:
SELECT * FROM PayrollTransactions ORDER BY PayrollYear DESC, PayrollMonth DESC, EmployeeId;

Check users:
SELECT * FROM AuthUsers ORDER BY Username;

Check departments:
SELECT * FROM Departments ORDER BY Name;

Check salary joined with employee:
SELECT s.*, e.EmployeeNumber, e.FirstName, e.LastName
FROM Salaries s
INNER JOIN Employees e ON e.Id = s.EmployeeId
ORDER BY e.EmployeeNumber, s.EffectiveFrom DESC;

Check payroll joined with employee:
SELECT p.*, e.EmployeeNumber, e.FirstName, e.LastName
FROM PayrollTransactions p
INNER JOIN Employees e ON e.Id = p.EmployeeId
ORDER BY p.PayrollYear DESC, p.PayrollMonth DESC, e.EmployeeNumber;

11. BUSINESS FLOWS
------------------
11.1 Employee creation flow
Frontend:
- Employee Management dialog collects employee data
- Department dropdown calls department API
- submit sends POST /api/employee

Backend:
- EmployeeController validates department existence
- validates employee number, email, and account number uniqueness
- creates employee row in Employees table

Result:
- employee appears in employee table
- employee becomes selectable in salary form

11.2 Salary creation flow
Frontend:
- Salary dialog selects employee by employee number
- user enters salary amounts and effective dates
- submit sends POST /api/salary

Backend:
- SalaryController validates employee existence
- validates deduction amount logic
- if employee already has active salary, current salary is closed by setting EffectiveTo
- new salary row inserted

Result:
- salary appears in salary section
- effective salary becomes usable by payroll generation

11.3 Salary update flow
Frontend:
- edit dialog loads current salary values
- EffectiveTo can be updated
- update sends PUT /api/salary/{id}

Backend:
- salary is updated
- PayrollGenerationService.RegenerateEmployeePayrollAsync(employeeId) runs
- this recalculates current and recent months for that employee

Result:
- salary table updates
- relevant payroll rows are regenerated

11.4 Payroll generation flow
Frontend:
- Payroll dashboard sends POST /api/payroll/generate-monthly
- success snackbar shows generated/updated/skipped counts

Backend:
- PayrollGenerationService checks all active employees
- finds salary that overlaps selected month window
- creates new payroll rows if missing
- updates existing payroll rows if they already exist
- skips employees with no salary setup

Result:
- payroll report changes
- recent payroll transaction list updates

11.5 Monthly report flow
Frontend:
- Payroll dashboard calls GET /api/payroll/report?year=...&month=...
- report is used for summary cards and xlsx export

Backend:
- PayrollController pulls payrolls for that month
- calculates totals from mapped rows

11.6 Admin user creation flow
Frontend:
- admin creates user from Profile screen
- sends POST /api/auth/users

Backend:
- DatabaseAuthUserStore inserts into AuthUsers table
- users persist after API restart


12. HOW PAYROLL CALCULATION WORKS
---------------------------------
Current payroll formula in PayrollGenerationService:
- baseSalary = salary.BasicAmount
- bonuses = salary.AllowanceAmount + request.AdditionalBonus
- grossPay = baseSalary + bonuses
- taxes = grossPay * (taxPercentage / 100)
- totalDeductions = taxes + salary.DeductionAmount + request.AdditionalDeductions
- netPay = grossPay - totalDeductions

Important notes:
- generation can now update existing payroll rows for the same month
- salary validity now uses month overlap logic, not only first day of month
- salary updates also trigger employee payroll regeneration


13. HOW USER PERSISTENCE WORKS NOW
----------------------------------
Old behavior:
- users were stored only in InMemoryAuthUserStore
- created users disappeared after restart

New behavior:
- users are stored in AuthUsers SQL table
- database-backed store file:
  src/HRMS.API/Auth/DatabaseAuthUserStore.cs
- startup applies migrations automatically
- startup seeds appsettings AuthUsers only if they are missing

This means:
- admin-created users remain after restart
- reset password remains after restart
- changed password remains after restart

18. HOW TO ANSWER SOMEONE ABOUT THIS PROJECT
--------------------------------------------
Short explanation:
This is a full HRMS application built with Angular frontend and .NET 8 backend. Employees are created first, then salary revisions are assigned to employees, and payroll is generated monthly based on effective salary records. All data is stored in SQL Server. Authentication uses JWT, and admin-created users are now persisted in the database.

Medium explanation:
The frontend is a standalone Angular app that talks to a .NET Web API using an ApiService and auth interceptor. The backend uses controllers, repositories, and a payroll service on top of Entity Framework Core. Employees belong to departments, employees have salary revisions over time, and payroll rows are generated from effective salary ranges. Admin and HR roles access the protected modules.

Detailed explanation:
The application has Angular routes for login, dashboard, employee management, salary management, payroll dashboard, profile, help center, and activity log. The backend exposes 20 endpoints across Auth, Department, Employee, Salary, Payroll, and Health controllers. Data is stored in SQL Server with EF Core migrations. Payroll logic calculates gross, tax, deductions, and net pay from the effective salary window for the selected month. UI counts, reloads, exports, and persistence are all wired through the frontend services and backend controllers described above.


19. IMPORTANT CAVEATS / KNOWN NOTES
-----------------------------------
- Activity Log is not a full real backend log system yet.
- Angular production build currently has bundle/style budget warnings or errors, but dev server runs.
- Swagger is enabled only in Development environment.
- Passwords are currently stored as plain text in AuthUsers. This works functionally but is not production-safe. In production, passwords should be hashed.
